# 游戏配套 Wiki 开发文档

文档版本：0.9 · 更新日期：2026-09-19
开发分支：`wiki` · 游戏核对基线：`v0.19.0`
当前状态：资料站、模拟器、官方攻略热更新、用户投稿（默认自动通过，可切换人工审核）、六词条攻略、搜索/更新页优化与 Wiki SQLite 存储迁移已在本地实现；生产部署和游戏 Release 尚未执行。

## 1. 目标与范围

为玩家提供无需登录即可访问的资料站，支持查询物品、了解玩法、阅读攻略，以及在不消耗游戏资产的情况下比较配装和模拟熔炼。

已确认：本版包含资料查询、玩法攻略、官方攻略热更新、用户投稿（默认自动通过）、配装模拟器、熔炼模拟器；两个模拟器不是后续可选项。当前分支已完成上述功能、构建检查和本地验收；生产发布待单独执行。

本文中的页面结构、数据格式、技术拆分和性能指标属于建议实施基线；后续调整应同步写入 [CHANGELOG.md](CHANGELOG.md)。游戏行为以对应版本的实际计算代码及配置为准，不直接把旧指南、代码注释或示例数字当成规则。

| W02 | 全站搜索 | 钓点、渔获、材料、组件底材、宝匣、词缀、攻略与工具联合搜索；简称、分类过滤、条目贴图与轻量详情卡片 |

| W07 | 熔炼模拟器 | 只读复制真实组件，主副件与词缀选择、投料、宝珠、残片、资源参考、结果分支、单次及批量模拟、产物继续模拟 |

### 1.2 后续扩展

自动寻优配装、在线收藏同步、评论、实时市场估值、独立重铸/开箱模拟器暂不进入本版。用户攻略只复用现有登录态，不读取或修改真实资产。

两个模拟器可通过同域登录态读取 `GET /api/wiki/simulator/inventory`。接口只返回名字、金币、库存、当前装备、已存钓竿和占用参考，禁止缓存及非 GET 请求。不能改用 `/api/me`，因为它会检查自动出售；钓竿视图计算必须对副本进行，以免辅助函数补齐真实存档字段。原始背包只驻留页面内存，编辑器接收深拷贝，刷新背包不覆盖编辑中的模拟方案。

背包数量用于参考，不限制自由试算。熔炼复用 `GameData.smeltPlanOf` 和 `GameData.simulateSmeltPlan`；单次和批量试验不累计扣减资源，“用结果继续模拟”只替换本地主件。方案保存和产物带入仅写 Wiki 专用的浏览器存储键，禁止调用真实工坊、穿戴、出售、交易和账号写入接口。

首版不执行真实装备、熔炼、出售、交易等操作；不要求用户输入游戏密码或管理员凭据。

## 2. 信息结构与使用路径

### 2.1 页面结构

建议使用可直接访问的静态页面路径，保证刷新、收藏和转发后仍可打开：

| 当前路径 | 内容 |
|---|---|
| `/wiki/` | 首页 |
| `/wiki/search/index.html?q=静水湖` | 搜索结果 |
| `/wiki/grounds/index.html` | 钓场、钓点列表 |
| `/wiki/grounds/index.html?ground=<id>&spot=<id>` | 钓点详情 |
| `/wiki/guides/index.html?slug=<slug>` | 攻略正文 |
| `/wiki/guides/submit.html` | 登录用户提交攻略 |
| `/wiki/guides/index.html?my=1` | 我的攻略与审核状态 |
| `/wiki/tools/build.html` | 配装模拟器 |
| `/wiki/tools/smelt.html` | 熔炼模拟器 |
| `/wiki/updates/index.html` | 面向玩家的更新记录 |

**托管决策**：首版由游戏服务器在同一个域名下托管 `/wiki/`，Wiki 显示名称为 `WIKI`。静态构建产物部署到游戏服务器可托管的 Wiki 目录，页面使用相对路径请求 `/api/version?profile=wiki` 与 `/shop`，保持同源访问，不新增独立静态托管、子域名或 CORS 配置。游戏服务重启期间 Wiki 可跟随短暂不可用，这是首版接受的代价；后续如流量增长，再评估仍保持 `/wiki/` 路径的同域名静态目录拆分。

部署根目录由构建参数指定，不在脚本中写死域名；本地预览必须与正式 `/wiki/` 前缀保持一致的路径计算。

### 2.2 核心路径

1. 搜索“龙宫宝珠” → 查看获取地点、用途 → 进入熔炼指南或带入模拟器。
2. 查看组件底材 → 比较词缀池和区间 → 添加到配装 → 选择钓点 → 与另一套配装对比。
3. 查看材料 → 了解对应催化词缀 → 带入熔炼方案 → 查看消耗与成功/失败结果。
4. 阅读“刷材料”攻略 → 打开参考配装 → 调整组件 → 保存并分享方案。
5. 登录玩家打开贡献攻略 → 填写草稿 → 提交 → 默认自动通过并立即公开；人工审核模式下在我的攻略查看待审核 / 已通过 / 已拒绝状态。

带入模拟器时，若只有底材而没有完整实例，应进入编辑状态；不能把“所有词缀全满”的假设组件伪装成真实掉落。

### 2.3 资料边界与钓点数据规范

Wiki 不再维护独立物品图鉴，也不复制游戏内图鉴的完整数据。鱼类、材料、组件底材、宝匣与词缀的完整详情以游戏内图鉴为准；Wiki 搜索只为这些条目提供缩略图、一行摘要与轻量详情卡（部位、词缀池、产出钓点、用途/成本），避免同一目录在两处展示后出现版本漂移。

钓点条目保留以下字段：所属钓场、开放状态、增益、独立间隔、独立上鱼率、当前有效掉落目录与权重。规则、目录、开放状态、掉落权重和概率来自 `/api/version?profile=wiki` 的规则快照；实时收购价是易变经济状态，不属于规则快照。规则快照不可用时，钓点页与模拟器不得显示当前概率或执行计算。

### 2.4 首批文章

- 新手首小时流程：稳定产鱼、出售普通鱼、保留材料与逐步换装。
- 产量优先级：钓速、技巧、双钓与材料、稀有度、体型的边界和取舍。
- 钓点选择：按目标查看当前有效权重，并用模拟器比较候选钓点。
- 七部位五词条参考配装与实测成本样本。
- 五词条构建路线：催化制件、高保留转移与逐项验收。
- 六词条路线：2 词池神话突破件 + 多段补缀 + 残片保留；每段配方、概率、成本与止损。
- 词缀来源机制：池内/池外/突破/催化的区分、补缀 3 条上限、保留概率公式与失败保护。
- 工坊止损：熔炼失败、补缀失败与保留缺口的处理。
- 资源循环：金币、材料、市集、直接交易与自动售出。
- 装备迭代与库存清理：先判断来源区间和 donor 价值，再决定清仓。
- 断线续钓、数值不一致、组件锁定、交易数量与攻略更新的常见问题。

每篇攻略写明目标、前提、步骤、取舍、适用版本；“推荐”与“规则事实”明确区分。收益攻略说明价格、钓点和配置假设。

## 3. 配装模拟器

当前实现：`/wiki/tools/build.html`，源码为 `frontend/wiki/tools/build.js`。

### 3.1 输入与编辑

- 部位使用游戏 `ROD_PARTS` 目录，不另维护七个部位的副本。
- 每个部位可为空/标准件，或选择底材、品质、词缀类型、数值及来源。
- 组件选择支持部位、名称、品质、词缀过滤；显示正负值与可用区间。
- 保留词缀来源 `src` 与 `srcExplicit`，避免池外、突破、催化范围被混淆。
- 选择钓点与配置快照，查看全服加成、钓点增益和独立覆盖值。
- 支持清空部位、复制方案、重命名、重置、从攻略载入参考方案。

组件输入分为“按当前规则编辑”和“自由试算”。前者校验部位、词缀类型、来源与区间，并区分自然生成和工坊产物；不能仅凭品质上限拒绝合法工坊件。后者允许研究超出常规范围的有限数值，始终标记为假设数据，不承诺可在游戏获得。

未知 ID、非有限数字、重复词缀、错误部位及不支持的来源均给出具体提示。不能仅凭神话品质声称拥有已验证的真实获取记录。

### 3.2 结果

| 结果 | 展示要求 |
|---|---|
| 六类词缀合计 | 原始组件合计、钓点修正、参与各公式的实际数值 |
| 抛竿间隔 | 毫秒和秒；显示上限、最短间隔或钓点独立覆盖是否生效 |
| 上鱼率 | 使用当前快照公式或钓点覆盖，说明计算来源 |
| 双钓 | 单次追加概率、成功上钩后 1/2/3 件的概率与期望件数 |
| 理论产出 | 每小时抛竿数、理论成功上钩次数、理论掉落总件数 |
| 稀有度/材料/体型 | 效果解释及参与计算的值；不冒充最终掉落概率、售价或最大体型 |
| A/B 对比 | 同一快照、同一钓点下的绝对差与相对差；基线为零时不显示无穷百分比 |

“每小时理论掉落总件数”包括鱼、材料和组件，不写成“每小时鱼数”；计算不含断线、切点或人为操作耗时，不等于金币收益。

### 3.3 计算要求

计算优先复用现有前后端共享实现；确需迁移服务端独有纯函数时，服务端正式路径与 Wiki 必须调用同一实现，并完整保留截断、舍入、默认值与覆盖优先级：

1. 汇总七个部位词缀。
2. 抛竿间隔优先使用有效的钓点独立间隔；当前实现中该路径直接返回，不再套通用最短间隔。
3. 普通路径先计算组件钓速与全服加成的有效值，再乘钓点钓速系数，最后舍入并应用最短间隔。
4. 上鱼率优先使用钓点独立值，否则使用现有安全表达式解析器及相同变量语义；禁止另用 `eval` 实现。
5. 双钓令 `A = max(0, 有效双钓值)`，`B` 为归一化后的世界基础双钓概率：

```text
p = 1 - (1 - B) × (1 - A / (A + 100))
P(1 件 | 上钩) = 1 - p
P(2 件 | 上钩) = p × (1 - p)
P(3 件 | 上钩) = p²
E(件数 | 上钩) = 1 + p + p²
理论掉落总件数/小时 = 3,600,000 / 间隔毫秒 × 上鱼率/100 × (1 + p + p²)
```

原始属性、间隔专用钓速、上鱼公式里的变量不一定相同，必须分别传递。上限提示应针对具体指标：间隔触底不代表在自定义上鱼公式中继续堆钓速必然无效。

### 3.4 保存与分享

- 本地保存建议使用独立命名空间 `fishing-wiki:builds:v1`，提供导入、导出和逐项删除。
- 首版至少提供链接和方案码两种分享方式，内容是组件与条件，不含游戏账号或资产信息。
- 分享数据带 `schemaVersion`、`rulesVersion`、`gameVersion`、`snapshotId`、`configHash`；同一方案使用同一规则和快照才能复现。旧快照不再可用时提示无法原样复现，允许另存为当前规则后比较。
- 正式服务器快照按 `snapshotId` 与 `configHash` 解析；本地 fixture 与显式研究模式必须内嵌完整规则或使用可访问的归档，不能只带本机 ID。
- 链接建议用 URL fragment 存方案。超长内容提示改用方案码或文件；解码前后均限制大小（建议解码后不超过 64 KiB）。自由试算方案必须带研究模式标记，分享与结果页不得显示为“官方可获取配置”。
- 未知版本不能静默使用最新规则重算；提示无法复现，并允许用户另存为当前版本后比较。
- 浏览器存储不可用或配额不足时保留当前编辑状态，提示导出，不阻断计算。

## 4. 熔炼模拟器

当前实现：`/wiki/tools/smelt.html`，源码为 `frontend/wiki/tools/smelt.js`。

### 4.1 操作区

主件、副件、保留词缀、投料、宝珠、保护残片与结果预览在同一工作区。桌面两栏，手机按输入→概率/费用→结果排列；修改输入立即更新确定性预览，不自动执行随机模拟。

输入规则：

- 主副件必须同部位，各选一条实际存在的词缀，所选类型不同。
- 同签名主副件表示使用两件等价组件，费用摘要明确写出数量，不要求连接真实背包。
- 投料数量为非负整数，种类与总量按配置限制；禁止重复材料行。
- 数量最多的材料决定补缀类型，并列时沿用 `smeltLoadOf` 的固定目录顺序，不能随机或按用户输入顺序处理。
- 区分普通投料、龙宫宝珠、保护残片；残片若同时作为投料与保护材料，应合并展示总消耗，但各自独立参与计算。
- 残片保护资格按 `canRecast`、池外词缀和配置上限校验。默认投入 0，卸下或更换成不合格主件时清空并提示。
- 切换组件后，对失效的所选词缀、补缀材料和保护条件重新校验。

### 4.2 确定性预览

展示总金币、每种材料数量、副件消耗，以及下列结果：

| 指标 | 定义 |
|---|---|
| 熔炼成功率 `S` | 按 `smeltRatesOf` 计算 |
| 成功后的补缀概率 `E` | 条件概率；不能当成最终获得新词缀的概率 |
| 主/副选中词缀落成率 | `S`，指成功产物里的重掷词缀，不包含失败后原词缀存续 |
| 补缀落成率 | `S × E`，公式中概率使用 0～1 |
| 完全成功 | 与游戏 `smeltSuccessProbs` 一致：有补缀时 `S × E`，无补缀时 `S` |
| 成功后的池外保留概率 `R` | 根据突破词缀数和残片数量计算，独立列出 |
| 成功且保留命中 | `S × R`，并说明同类型去重可能导致没有实际追加 |

“完全成功”不默认包含残片保留。若增加“补缀与保留同时命中”，单独命名并按实际判定关系计算，不改变游戏已有标签的含义。

预览逐条展示当前值、预计区间、区间来源、词缀身份与落成概率。对池外保留分支显示原值与去重结果；不要把所有池外词缀都标成宝匣突破词缀。

### 4.3 结果分支

1. 熔炼成功：保留主件底材与品质，主副所选词缀重掷；其他原词缀不会无条件保留。
2. 补缀：仅在熔炼成功后独立判定；成功后才追加目标词缀，范围与来源按现有规则。
3. 残片保留：成功后只掷一次保留判定；命中后按原值、原来源追加符合条件的池外词缀，同类型去重。不是每个词缀各自独立掷骰。
4. 熔炼失败且未保护：主件失去所选词缀，其他词缀及来源保留；允许结果没有词缀。
5. 熔炼失败且投入有效保护残片：主件所选词缀也保留；副件、材料、宝珠、残片与金币仍按规则消耗。

补缀条数上限与残片保留追加是不同阶段，不能用补缀上限截断整个最终产物。宝珠的边界取值代表两次掷骰后按规则选择更靠近边界的结果，不等于必定最大值或必定正向提升。

### 4.4 单次和批量模拟

- 单次模拟展示结果组件、词缀来源、成功/失败类型和完整消耗，可把产物带入配装模拟器。
- 批量默认采用“同一输入独立重复试验”，建议支持 100、1,000、10,000 次；每轮恢复原主副件与材料。
- 明确说明批量不代表连续强化同一件主件，不估算真实库存能否支撑。
- 使用可注入的带种子随机数生成器，保存种子、算法版本、试验次数和规则版本，可复现实验。
- 展示熔炼成功次数、补缀落成次数、保留命中/实际追加次数、结果条数分布和数值分布摘要。
- 理论概率与样本频率分栏展示；批量成本为次数乘以单次成本，不把样本平均数声称为保底。
- 批量任务使用 Worker 或分片，支持进度、取消；更改输入后旧结果标为过期，不覆盖新预览。
- 首版不提供无限次数，也不通过调用真实熔炼接口产生模拟样本。

## 5. 数据与规则同步

### 5.1 权威来源与硬性约束

服务端是唯一权威。Wiki 的物品目录、钓点配置、掉落权重、公式、范围、概率和费用不得另行手写、猜测或长期缓存；页面、模拟器和文章中的数值必须能追溯到服务端生成的同一份快照。

实现必须满足以下约束：

1. **共用规则实现**：优先复用现有 `frontend/js/data.js` 这类前后端已共享的实现；确需迁移服务端独有函数时，服务端正式路径与 Wiki 必须调用同一实现。禁止维护“长得像”的第二套公式。
2. **服务端快照**：正式 Wiki 优先复用并扩展现有公开接口获取白名单快照，不先新建平行接口。快照包含目录、钓点、公式与配置，并带有 `gameVersion`、`rulesVersion`、`configRevision`、`configHash` 和生成时间。
3. **版本与配置闸门**：Wiki 启动和计算前校验快照来源。规则版本不兼容、游戏版本不匹配、配置哈希无法确认或快照结构校验失败时，禁用相关数值和模拟器，展示“规则不可用”，不能静默回退到默认值或旧缓存。
4. **实时性要求**：正式数值页和两个模拟器使用当前快照。`profile=wiki` 使用 `Cache-Control: no-cache` 与 `ETag: snapshotId`，Wiki 启动、窗口回到前台和计算前校验，并以不超过 5 秒的间隔轮询；连续 10 秒无法确认最新配置时禁用受影响计算。刷新失败时可以保留正文浏览，但不得继续显示可操作的过期计算结果。
5. **发布顺序**：游戏服务端与 Wiki 必须按同一发布清单发布。Wiki 规则实现先于服务端上线或落后于服务端时，生产环境均不得启用计算功能；只能显示“等待规则同步”的说明。
6. **本地开发例外**：单元测试和本地原型可使用由服务端代码生成的固定 fixture，并明确标记为 `fixture`；该类快照不得用于生产 Wiki。
7. **人工内容边界**：攻略可以写思路和取舍，但不得硬编码概率、区间和费用作为事实。文章只写取舍和流程；引用数值时引导玩家使用当前模拟器计算，不在正文硬编码概率、区间或费用。

接口调整必须先盘点现有能力，优先合并语义相同的返回；确需新增字段时挂到现有公开接口的明确 profile 下，并由同一个服务端组装函数提供，避免同一份配置在多个接口里各写一遍。不能直接暴露 `config.json`、管理接口、存档、会话、账号、市场私数据或完整后台响应；也不得为了图省事把服务端内部对象整包下发。

### 5.2 现有接口盘点与复用决策

2026-09-18 在临时数据目录与临时端口启动本地服务实测；初测基线为 `v0.16.6 / a9e1924`，合入 `v0.17.0 / 97d3597` 后复核：`backend/server.js` 无变化，`frontend/js/data.js` 仅版本号变化，下列接口结论继续适用：

| 现有接口 / 通道 | 实测与代码结论 | Wiki 复用决策 |
|---|---|---|
| `GET /api/version` | 公开、无需登录；默认响应约 1.4 KB，已返回版本、功能开关、组件配置、鱼类体型配置、抛竿配置、经济与掉落配置、自动售出、宝匣、熔炼、记录配置 | 作为唯一公开规则入口的基础，继续复用，不新建平行接口 |
| `GET /api/grounds` | 公开、无需登录；默认响应约 4.0 KB，实测 4 个钓场、9 个钓点，返回经掉落倍率换算后的有效权重 | 保留给现有游戏端和测试；Wiki 的规则 profile 内部复用 `groundsWithDrop()`，避免复制组装逻辑 |
| `GET /shop` | 公开、无需登录，返回系统收购当前价、基准价与销量；这是易变经济状态，不是规则配置 | 经济页需要实时收购价时复用；不并入规则快照，也不参与 `configHash`。Wiki 使用时要求 `Cache-Control: no-store`，页面可见时 5 秒刷新，10 秒无法确认则隐藏当前价 |
| `GET /api/features` | 仅返回 `features`，该字段已包含在 `/api/version`，属于重复接口 | 标记为兼容别名并逐步迁移测试；Wiki 不调用 |
| `GET /events`（SSE） | 需要登录，`init` 与配置广播面向在线玩家 | Wiki 不依赖 SSE；使用公开规则接口轮询或 ETag 刷新 |
| `GET /api/admin/world` | 管理员专用，含经济日志、后台完整配置等不适合公开的数据 | 不复用，不作为 Wiki 数据源 |
| `POST /api/admin/simulate` | 已有服务端权威配装试算，但管理员专用 | 不暴露管理员凭据；后续只复用其内部 `simulateRod()` 逻辑，不复用这个管理端点 |
| `frontend/js/data.js` | 后端与前端已共用；包含组件生成、词缀区间、熔炼概率、费用、催化范围和安全表达式工具 | 已新增共享配装计算与可注入随机数；服务端正式路径委托同一实现，Wiki 后续直接复用 |

因此 M1 不新增 `/api/wiki/rules`。当前实现已扩展现有 `GET /api/version?profile=wiki`，并由服务端组装函数同时服务默认响应与 Wiki profile：

- 不带 profile 的现有响应保持轻量，兼容当前前端轮询；默认与 Wiki profile 都由同一个内部组装函数生成，不允许两处手拼同一配置。
- `profile=wiki` 返回独立的 `snapshot` 对象，不重复展开默认响应字段；内容为公开目录、`groundsWithDrop()` 结果、公式与一致性元数据。
- Wiki 的规则数据只调用这一个入口；`/api/grounds` 暂时保留为现有客户端兼容接口，后续评估是否降级为别名或移除。
- `/api/features` 与 `/api/version` 重复，后续标记废弃并迁移调用方。
- 服务端、游戏端和 Wiki 端不得各自拼装同一份规则；公开规则字段只允许一个权威组装函数。

`profile=wiki` 已返回 `biteFormula`、`doubleBase`、`rareK`、公开目录、钓点有效权重、`rulesVersion`、`configRevision`、`configHash`、`generatedAt` 和 `sourceCommit`。响应外形固定为 `{ profile, version, snapshot }`，`snapshot` 使用第 5.3 节契约。响应使用 `Cache-Control: no-cache` 与 `ETag: snapshotId`，并支持 `If-None-Match` 304；`sourceCommit` 由发布流程注入，不在生产机执行 Git 命令探测。若跨域部署，继续使用现有 `ALLOWED_ORIGINS` 白名单，不放宽为任意来源。

### 5.3 快照契约

| 字段 | 用途 |
|---|---|
| `schemaVersion` | 数据结构兼容版本，未知版本拒绝计算 |
| `gameVersion` / `sourceCommit` | 正在运行的游戏版本及完整提交 SHA |
| `rulesVersion` | 共享规则实现兼容版本；仅代码行为变化时更新，不由运行时配置覆盖 |
| `serverInstanceId` / `configRevision` | 区分服务器实例与配置变更代数，单调递增 |
| `snapshotId` / `configHash` | `snapshotId` 由服务器实例、配置代数和哈希派生，用作 ETag；`configHash` 是规范化公开规则数据的 SHA-256，用于内容一致性校验 |
| `sourceKind` | 生产只允许 `server`；本地测试允许 `fixture`；`custom` 仅限显式研究模式 |
| `generatedAt` | 服务端 UTC 生成时间，界面转换为用户本地时间 |
| `catalog` | 鱼、材料、组件、宝匣、词缀和部位目录 |
| `grounds` / `spots` | 公开钓场、钓点、有效掉落权重、增益与覆盖配置 |
| `rulesConfig` | 抛竿、上鱼、双钓、组件区间、宝匣、熔炼及公开经济规则 |

快照可以按请求组装，或在服务端缓存后原子替换；两者都必须使用当前 `world` 配置和共享目录，并输出规范化 JSON。`configHash` 只覆盖目录、钓点、公式和规则配置，不包含 `generatedAt`、`snapshotId`、实时价格或其它易变展示状态。配置保存后递增 `configRevision`；即使无关配置导致代数变化，哈希也能判断规则是否实际改变。

输入校验检查关联 ID、重复项、必填字段、有限数值、有效区间、配置范围、公式可解析性、版本兼容性和 `configHash`。生产构建不内嵌正式快照；`wiki:build` 只构建静态内容，`wiki:verify:server` 才要求连接指定服务端并验证 profile 契约。

建议纯函数接口：

```text
calculateBuild({ slots, spotId }, snapshot) -> BuildResult
validateSmelt(input, snapshot) -> ValidationResult
previewSmelt(input, snapshot) -> SmeltPlan
simulateSmelt(plan, snapshot, rng) -> SmeltOutcome
```

`SmeltPlan` 包含规范化输入、消耗、概率、区间和分支说明。背包余额、锁定与扣款属于游戏事务层，不进入 Wiki 计算核心。

### 5.4 当前代码的复用边界

| 现有位置 | 已有能力 | 开发动作 |
|---|---|---|
| `frontend/js/data.js` | UMD 数据目录、组件实例与来源、工坊计算和安全表达式工具 | 与服务端共用；当前页面一次只消费一个快照，计算函数显式传入规则，避免多快照并发污染 |
| `backend/server.js` 的配装/钓鱼函数 | `bdEffectsOf`、`intervalFor`、`castInfoOf`、`doubleProbOf`、`simulateRod` | 已最小迁移到现有共享 `data.js`；服务端保留同名适配函数并调用同一实现，Wiki 不复制公式 |
| `backend/server.js` 的工坊函数及路由 | `planSmelt`、`smeltRangesOf`、随机结果与结算 | 拆开规则计划、随机结果、资产事务；服务端与 Wiki 共用前两层，禁止把库存校验复制进 Wiki |
| `backend/server.js` 的公开接口 | `/api/version` 已承载大部分公开配置，`/api/grounds` 已承载有效掉落权重，`/shop` 承载实时收购价 | 扩展现有 `/api/version?profile=wiki`，由单一组装函数复用 `groundsWithDrop()`；不新增平行规则接口，`/api/features` 后续标记重复，实时价格继续用 `/shop` |
| `frontend/js/ui.js` | 组件选择与熔炼预览的交互参照 | 复用数据契约和视觉资产，不直接加载整个游戏界面与网络状态层 |
| `GUIDE.md`、`README.md`、`VERSIONS.md` | 内容素材与历史背景 | 逐条核对后改写成玩家文章；数值不作为独立事实源 |

禁止直接 `require` 整个 `backend/server.js` 来计算或导出，它包含监听、存档及世界状态等副作用。多个模拟器或 A/B 两方案不得通过全局配置切换互相污染。

### 5.5 一致性验收

- 服务端真实计划函数与 Wiki 共享函数必须在同一批固定输入上逐字段一致，覆盖配装、上鱼、双钓、熔炼校验、费用和概率。
- 抽样对比线上接口返回的计算结果与 Wiki 渲染结果，差异不为零即阻断发布。
- 后台修改钓速、上鱼公式、掉落权重、组件区间、宝匣或熔炼配置后，Wiki 必须在验收规定时间内取得新 `configRevision`；未取得前禁用受影响计算。
- 快照缓存只能按 `configHash` 复用，不能按 URL 或时间粗暴缓存；生产页面禁用旧快照计算。
- 规则模块版本与游戏版本不匹配时，资料正文可提示维护，但模拟器必须禁用。
- 发布清单必须记录服务端提交、Wiki 提交、快照哈希、生成时间与验证结果。

### 5.6 已发现的文案漂移

- `data.js` 的 `smeltRatesOf` 实际为 `baseRate + failPerMaterial × total`；基线默认每份为 `-2`，增加投料会降低熔炼成功率。附近注释及 README 的部分文字方向相反，不能照搬。
- `GUIDE.md` 的固定每片 10% 是简化旧说法；当前默认公式为 `10 - breakthrough × 0.5`，再按残片数量计算，并执行夹取和舍入。
- 旧指南与游戏内部分提示把残片失败保护写成「只保护主件选中的词条」；当前共享实现（`simulateSmeltPlan` 的 `protectAffix` 分支）在残片投入大于零且熔炼失败时保留主件全部词条，不投入残片才移除主选词条。Wiki 文档与攻略按当前实现描述，游戏内文案差异另行统一。
- 旧说明中的词条数量、物品总数、概率和费用都可能随目录及后台变化，应从服务端快照生成，不手写多份。

这些发现是内容核对任务，不代表已经修改游戏逻辑或旧指南。

### 5.7 攻略热更新与用户投稿契约

攻略正文与玩家更新记录是人工内容，不再随 `frontend/wiki/js/content.js` 手写维护：

- 内置种子内容放在 `frontend/wiki/content/content.json`，用于新环境和静态开发兜底；`content.js` 只保留空容器，避免同一份正文出现两份会漂移的来源。
- 存储：数据目录 `wiki.db`（Node 内置 `node:sqlite`，WAL，零第三方依赖；要求 Node >= 22.13）。表结构：`guides`（官方/玩家共用，`kind` 区分）、`guide_sections`（正文段落）、`updates`、`guide_revisions`（修订历史）、`wiki_meta`（`official_revision` / `user_revision` / `official_updated_at`）。
- 公开读取分两层：`GET /api/wiki/content` 返回 `{ revision, updatedAt, guides, updates }`，guides 只含元数据（id / kind / status / title / category / summary / tags / aliases / 作者 / 更新时间）；正文用 `GET /api/wiki/guides/<id>` 按需读取；列表分页与搜索用 `GET /api/wiki/guides?page&pageSize&q&kind&category`。均使用 `Cache-Control: no-cache` 与内容 ETag，并支持 `If-None-Match` 304。
- 内容 ETag 直接由 `official_revision` 与 `user_revision` 生成（`"wiki-content-<o>-<u>"`），不再对全量 JSON 做哈希；正文不参与 5 秒轮询。
- 管理员通过 `POST /api/admin/wiki/content` 保存整份 JSON，或 `reset: true` 恢复内置内容。请求走管理员 MFA 会话和管理审计，服务端校验 ID、日期、段落类型、列表与长度上限。
- 官方保存写入 SQLite：`POST /api/admin/wiki/content` 在事务里整批替换官方 guides/updates 并推进 `official_revision`，不写入 `config.json`，也不推进规则快照的 `configRevision`。攻略更新与规则配置变更互不污染。
- Wiki 前端每 5 秒轮询元数据接口（ETag 命中 304），打开攻略详情时按 id 拉取一次正文并在本地缓存；内容 revision 变化时缓存自动失效。静态开发环境在接口不可用时回退读取 `/wiki/content/content.json`（该文件含完整正文）。
- 管理后台「📚 Wiki攻略」页分为官方内容与用户投稿审核两个区域；官方内容提供当前版本、攻略列表、JSON 编辑、格式化、保存发布和恢复内置操作。
- 官方保存必须携带 `baseRevision`，服务端不匹配时返回 409，防止 stale save 覆盖其他管理员修改。
- 玩家投稿在 `guides` 表内以 `kind='user'` 独立存储，审核状态（pending/approved/rejected）与软删除标记同表维护，写入推进 `user_revision`；`guide_revisions` 记录提交 / 审核 / 删除 / 官方保存的快照。
- 旧版 `wiki.json` / `wiki-guides.json` 只在 SQLite 为空时首次导入（含 pending/rejected/deleted 状态与 revision），导入后保留作备份，不再读写。
- 备份：停服后复制 `wiki.db` 即可（WAL 会在正常关闭时合并）；如需运行中复制，必须连同 `wiki.db-wal` / `wiki.db-shm` 一起复制。
- 公开接口只下发官方攻略和 `status=approved` 的用户攻略；pending、rejected、deleted 一律不下发。
- 用户提交接口为 `POST /api/wiki/guides/submit`，使用现有 Cookie/Authorization 会话和 CSRF 约束，不接受 body token。
- 审核模式由 `WIKI_GUIDE_AUTO_APPROVE` 控制：默认自动通过（`status=approved`、`reviewedBy=auto`，提交后立即公开）；设为 `0` 后重启服务端恢复「提交 → pending → 管理员审核」流程。
- `GET /api/wiki/guides/my` 只返回当前用户自己的投稿和审核状态；`POST /api/wiki/guides/delete` 允许作者删除 pending 投稿，以及自动通过（`reviewedBy=auto`）的投稿，人工审核通过的投稿只能由管理员删除。
- 管理员使用 `GET /api/admin/wiki/guides` 查看投稿，`POST /api/admin/wiki/guides/review` 通过或拒绝，`POST /api/admin/wiki/guides/delete` 软删除。
- 审核接口要求 `expectedStatus` 匹配当前状态，防止并发重复审核；拒绝和删除必须填写原因，并记录 `reviewedAt/reviewedBy/reviewNote`。
- 频率限制从持久化投稿计算：24 小时最多 3 篇、同时 pending 最多 3 篇、两次提交至少间隔 10 分钟；服务器重启后仍生效。
- 用户输入只允许纯文本结构，服务端严格限制标题、分类、摘要、标签、段落类型、列表和 64 KB 单篇大小；前端使用 `textContent` 渲染，不插入用户 HTML。

攻略仍必须遵守人工内容边界：写流程、取舍、风险控制和样本说明；概率、区间和费用以当前规则快照、工坊页面或模拟器为准，不把一次样本写成保底。

## 6. 技术与目录方案

建议沿用 Node.js 与原生 Web 技术，Wiki 独立静态构建；运行时无需游戏登录和外部数据库，Wiki 内容使用 Node 内置 `node:sqlite` 单文件存储。页面运行时渲染目录、文章与模拟器，规则数据来自服务端快照，攻略正文来自 SQLite 并按需读取。Markdown 渲染器如需引入第三方构建依赖，应固定版本并禁用原始 HTML。首版托管跟随游戏服务器，发布时需要把 `dist/wiki/` 产物复制或部署到游戏服务器可托管的 `/wiki/` 目录，并验证同源 API 可访问。

```text
docs/wiki/                 # 开发文档与规划/开发日志
frontend/wiki/             # 同域托管入口、页面与静态种子
frontend/wiki/content/     # 官方攻略 content.json 与主线 versions.json
frontend/js/data.js         # 服务端与 Wiki 共享的数据目录与计算规则
tools/wiki/                # 版本同步、内容检查、静态构建与服务端契约验证
tests/wiki/                # Wiki 规则、投稿与浏览器回归
dist/wiki/                 # 构建产物，部署到游戏服务器 /wiki/ 静态目录
```

已提供 `npm run wiki:test`、`wiki:test:browser`、`wiki:sync`、`wiki:check`、`wiki:build`、`wiki:serve` 和 `wiki:verify:server`。

上线前还可以使用专门隔离的 Docker 测试环境；见 [DOCKER_TEST.md](DOCKER_TEST.md)。后续仅在需要本地离线内容样例时补充 `wiki:fixture`。`wiki:build` 不要求正式服务端在线，也不内嵌生产快照；`wiki:verify:server` 必须连接指定服务端并校验 profile 契约、哈希和一致性样例。

文章元数据至少包含 `id/title/category/aliases/tags/gameVersion/updatedAt/status/related`。站内交叉链接使用 ID 建立，构建时发现断链即失败；旧 ID 改名保留别名或重定向。

搜索排序建议：名称完全匹配 → 简称/别名 → 前缀与子串 → 标签/正文；中文无需用户输入完整名称。构建期索引只覆盖文章和静态别名；钓点必须在运行时来自当前规则快照并合并进搜索结果，不能用构建时的旧目录冒充当前数据。渔获、材料、组件底材、宝匣与词缀类型同样从规则快照建立运行时索引，Wiki 只提供名称、像素贴图、一行摘要与轻量详情（词缀池 / 产出钓点 / 用途成本 / 工具入口），不复制游戏内完整图鉴。输入防抖、键盘操作和无结果建议纳入首版。

## 7. 界面与质量要求

- 直接加载游戏 `style.css`、`pixel.css`、`responsive.css`、`mobile.css` 与 `smelt.css`；复用顶栏、侧栏、像素窗口框、按钮、输入框和工坊工作台类名，不另造一套 Wiki 视觉体系。
- 桌面沿用游戏顶栏 + 侧栏 + 内容区布局；手机优先搜索、分类入口和模拟器关键操作。
- 概率附带文字含义，正负属性同时显示符号，不能只靠颜色区分。
- 表单有标签、错误关联、键盘焦点；模拟器能全程用键盘操作。
- 适配 360px、390px、768px、1440px 宽度及桌面 200% 缩放，无关键按钮遮挡和页面横向溢出。
- 建议性能目标：索引加载后的搜索与常规计算 P95 小于 100ms；10,000 次模拟不阻塞界面，取消操作 300ms 内响应。验收记录浏览器、设备和输入规模。
- 静态正文具备标题、描述、面包屑和可索引链接；图片延迟加载，模拟器资源按需加载。
- 分享码和导入文件严格校验，不执行外来表达式脚本、不直接插入用户 HTML；未知配置版本提供可读错误。
- 用户攻略正文只允许纯文本结构，前端全部用 `textContent` 渲染；公开页面不出现待审核或已拒绝内容。

当前实施状态：M0～M4 已完成；M5 已完成本地静态检查、构建、服务端契约验证、无头浏览器渲染与交互回归。生产部署、正式 `SOURCE_COMMIT` 注入和游戏 Release 未执行，不能声称已上线。

### 8.1 规则测试矩阵

| 领域 | 必测场景 |
|---|---|
| 配装 | 空配置、七部位、负词缀、钓速封顶、最短间隔、钓点乘算、独立间隔低于通用最小值 |
| 上鱼 | 默认公式、自定义公式、上下界、独立覆盖 0%、未知/无效公式 |
| 双钓 | A=0、负值、高值，B=0/1；1/2/3 件概率和为 1，期望与分布一致 |
| 工坊校验 | 跨部位、同类型词缀、同签名两件、空词缀主件、重复材料、超量、多类型并列 |
| 工坊数值 | 0 投料/最大投料、成功率上下界、费用、宝珠边界选值、催化范围回退与副件区间 |
| 保护与来源 | 无残片、有效残片、无池外词缀、不同突破数量、失败保护、成功保留一次掷骰、同类型去重 |
| 配置隔离 | A/B 不同快照、多工具切换、设置覆盖后还原、未知版本拒绝 |
| 规则 profile | 默认响应与 Wiki profile 共用组装；哈希排除易变元数据；snapshotId 作为 ETag、no-cache、5 秒轮询、10 秒失联禁用 |
| 动态搜索 | 构建期文章索引 + 运行时快照目录（钓点与物品）合并；条目贴图、轻量详情与类型过滤可用；目录变更后旧条目不下发为新数据 |
| 内容存储 | SQLite 首次启动迁移旧 JSON、重启持久化、pending/rejected/软删除状态保留、revision 与 ETag 一致、正文搜索命中、分页边界、官方保存与用户投稿互不覆盖 |

### 8.2 本地 fixture 验算样例

以下仅用于本地测试和服务端/Wiki 共享规则的一致性验收，不代表线上配置；生产 Wiki 的展示值必须来自正式服务端快照：

- 双钓 A=100、B=0：追加概率 50%；上钩后 1/2/3 件为 50%/25%/25%，期望 1.75 件。
- 熔炼无投料、无宝珠：成功率 50%，金币 5,000，无补缀。
- 熔炼 20 份有效投料、无宝珠：成功率 10%，条件补缀率 95%，补缀落成率 9.5%，金币 23,000。
- 上例加入宝珠：熔炼成功率不变，金币 43,000，启用两次掷骰的边界选值规则。
- 主件有 1 条突破词缀，投入 10 片有效保护残片：条件保留概率 95%；不能写成必定保留。

### 8.3 页面与发布验收

- 搜索“静水湖”能找到钓场与钓点；渔获、材料、组件、宝匣、词缀结果带贴图并可打开轻量详情；攻略与工具结果可跳到对应页面和模拟器。
- 首页与更新页默认只突出最近一次更新；完整版本演进和更早内容能通过历史入口展开。
- 两套配装保存、刷新、导出、重新导入后，数值与词缀来源一致。
- 熔炼模拟结果可作为自定义组件带入配装；不合格输入不能执行模拟。
- 批量取消、更改输入、无存储权限、损坏分享码、未知版本都有可恢复的状态。
- 除攻略投稿外，Wiki 全流程不请求真实资产写接口；投稿不消耗游戏资产，未登录状态可完成查询和模拟。
- 规则不可用或无法校验时模拟器禁用计算；玩家页面不展示配置代数、配置哈希、快照时间等诊断信息。
- 展示实时收购价时复用 `/shop`，与规则快照分栏标注获取时间；接口失败时不显示旧价为当前价。
- 内容链接、图片、规则 profile 契约、构建输出均检查通过；Wiki 内容落盘为 SQLite（`wiki.db`），旧 `wiki.json` / `wiki-guides.json` 不再写入；生产部署与游戏版本发布单独执行和记录。

规则提取涉及游戏行为时运行相关工坊、钓鱼和浏览器回归，并按仓库要求完成 `tests/run-all.js`；另需执行服务端与 Wiki 的一致性对比。本次纯文档提交只检查格式、链接和引用，不声称完成上述功能测试。

## 9. 更新日志与维护流程

1. 需求改变时先修改对应章节，并在 [CHANGELOG.md](CHANGELOG.md) 标明“规划变更”。
2. 功能提交记录完成项、影响范围、适用游戏版本、实际验证结果与遗留限制。
3. 游戏数值或工坊规则改变时，更新共享规则、线上 profile 契约、参考方案、文章和一致性样例；旧分享方案保留版本提示。
4. 游戏版本号、Wiki 发布版本、规则版本、快照 ID 分开管理。仅文档更新不抬升游戏版本或创建游戏 Release。
5. 首版发布日志只列已完成并验收的功能；待开发事项保留在规划区，不写成上线公告。

已确定为硬性要求：正式 Wiki 的数据来源和计算规则必须与正式服务端一致，不能伪造、滞后或静默回退默认配置。接口方向已调整为复用优先：规则数据扩展现有 `/api/version`，实时收购价复用 `/shop`，不新建平行规则接口；语义重复的 `/api/features` 后续合并。规则刷新采用 ETag/no-cache 与 5 秒轮询、10 秒失联禁用；玩家页不再展示规则诊断字段或复制纠错模板，异常反馈走游戏内既有反馈入口。托管方式已确定为游戏服务器同域托管 `/wiki/`，显示名称为 `WIKI`；不再有阻塞实现的域名、托管和显示名称决策。
